        01 / Event-driven · Real-time
        
Real-time fraud screening

        
100–150 risky orders caught per week, 6–8 hours of manual review saved

        
  • Python
  • FastAPI
  • PostgreSQL
  • Shopify webhooks
  • GraphQL
  • React

      

      

        
Problem

        
Support checked risky orders by hand. Shopify's risk score sometimes arrives after the order is created, so some risky orders were never looked at.

        
What I built

        
A service that receives every new order, waits 90 seconds so Shopify can finish its own checks, then reads the order again. It matches the customer against the team's fraud records and Shopify's risk level. Known fraud is cancelled. Risky orders go to a review queue and support gets an email. A second webhook catches late risk updates, and a nightly job re-scans the last 26 hours as a safety net.

        
Result

        
100–150 risky orders flagged each week, saving support 6–8 hours of manual review. They now work from one dashboard with their own logins, notes, and approve / cancel buttons.

      

      
      

        Engineering notes
        
    
          
  • Anything that changes a real order (cancel, charge the card) sits behind one switch. It stayed off, with actions only logged, until the team trusted the results.
    • 
          
  • Before launch I found that orders were marked "cancelled" while the switch was off and no cancel was sent. Fixed it so the status and the email tell the truth.
    • 
          
  • The live webhook, the late-risk webhook, and the nightly re-scan share one pipeline, so all three behave the same. Running it twice is safe.
    • 
          
  • I checked the spec against real order data and found a case it missed: medium-risk orders were already charged, so only high-risk orders need an Approve button.
    • 
          
  • Every webhook is verified with an HMAC signature, so no one can send fake orders to the service.
    • 
        

      

    


    

      

        02 / Full-stack app · Marketing data
        
Wishlist app with marketing sync

        
2 weeks from first commit to production, with 150+ automated tests

        
  • TypeScript
  • Remix
  • Prisma
  • Liquid
  • App extensions
  • Klaviyo API

      

      

        
Problem

        
The store paid for a third-party wishlist app, and the data was locked inside it. Marketing could not email shoppers about the items they saved.

        
What I built

        
A custom Shopify app: heart buttons on product cards and pages, a "My Wishlists" page inside customer accounts, and an admin dashboard with the most-saved products and exports. Then a Klaviyo sync for "items on your wishlist" emails, and a conversion report that shows saved, then added to cart, then bought, by product or by variant.

        
Result

        
Replaced the paid app. Marketing now sends "still on your wishlist" emails with each shopper's own items. It launched behind an on/off switch, so rollback takes one click.

      

      
      

        Engineering notes
        
    
          
  • Klaviyo campaigns cannot read event data, only profile data. So the wishlist lives on the profile and in custom object records. I proved this by testing, because the docs don't say it clearly.
    • 
          
  • Klaviyo record IDs are global, not per customer. Each ID is a hash of customer + product, so one shopper's save can never overwrite another's.
    • 
          
  • The sync never blocks a shopper's save. It retries on rate limits but never waits more than 2 seconds on the shopper's request.
    • 
          
  • Found and fixed four bugs that only showed up in production (a server build issue, two CORS issues, and a per-store setup step), and wrote each one down for the team.
    • 
          
  • Privacy (GDPR / CCPA): a data erase endpoint the ERP calls to delete a customer across 6 tables in one database transaction, protected by Basic auth with a constant-time compare. Tracking sends IDs only, and only for wishlisted products.
    • 
        

      

    


    

      

        03 / Platform · Security
        
One auth service for every integration

        
5+ apps share one auth service. Setup for a new app went from days to minutes.

        
  • Python
  • FastAPI
  • PostgreSQL
  • OAuth 2.0

      

      

        
Problem

        
Every new script or app needed its own Shopify login setup for each store. Access tokens were spread across projects.

        
What I built

        
A small service that runs the Shopify OAuth flow once per store, stores the tokens in Postgres, and hands them to internal apps through an API-key protected GET /token/{store} endpoint.

        
Result

        
Fraud screening, product sync, the best-sellers service, and scheduled jobs all get their tokens from it. A new app skips auth setup and makes one API call instead.

      

      
    


    

      

        04 / Data sync · Multi-region
        
Catalog sync across four regions

        
4 stores kept in sync, with a preview before every change

        
  • Python
  • FastAPI
  • PostgreSQL
  • React
  • Shopify GraphQL
  • Job queue

      

      

        
Problem

        
Products are created in the main US store and had to be copied by hand into the Canada, EU, and Australia stores.

        
What I built

        
A new app, built from scratch and embedded in the US store admin. The team picks products or a collection, picks the target stores, and sees a dry-run preview first. Then a job queue splits the work into one item per product per store, and a background worker syncs fields, images, and metafields. It can create, update, archive, or delete.

        
Result

        
Built from scratch and launched in under two weeks. The team's feedback from the demo, like an Errors tab and simpler controls, went in the same day. One store failing never stops the others.

      

      
      

        Engineering notes
        
    
          
  • The job queue lives in Postgres. Workers claim items with FOR UPDATE SKIP LOCKED, so two workers never take the same item, and no extra queue service is needed.
    • 
          
  • Rate limits, network errors, and Shopify 5xx errors are retried with backoff. When Shopify throttles, the client waits exactly as long as its query budget needs. An item left "running" by a crashed worker goes back to the queue.
    • 
          
  • The first sync matches products by SKU and checks the title. Zero or two matches is an error, never a guess. After that, saved ID links are used.
    • 
          
  • "In sync" is a hash of the US data, saved after each sync, so unchanged products are skipped.
    • 
          
  • Each US image is linked to its copy. An update uploads only new images and never re-uploads unchanged ones.
    • 
          
  • Safety first: only approved stores can be targets. A product's URL never changes after it is created, so live links don't break. If a sync would delete variants, it is blocked. Archive and delete always show a preview first.
    • 
          
  • 45 automated tests.

        05 / Data pipeline · Reporting
        
Subscription reporting into Asana

        
4 stores rolled into one daily report, with no copying by hand

        
  • Python
  • FastAPI
  • PostgreSQL
  • Recharge API
  • Asana API

      

      

        
Problem

        
Leadership tracks a subscription product in Asana, but Asana can't pull numbers from the subscription platform.

        
What I built

        
A service that pulls orders and subscriptions for four stores into Postgres. It computes monthly revenue, new, active and cancelled subscriptions, and churn, then writes worldwide totals into Asana every day.

        
Result

        
Leadership sees fresh numbers every day, and no one copies data by hand anymore.

      

      
      

        Engineering notes
        
    
          
  • Revenue comes from orders, not charges, to match the platform's own report, so the numbers agree.
    • 
          
  • Sync is cursor-paginated and idempotent. Running it twice gives the same result.

Sales portal and ERP sync

        
30 → 2 min to create a client order

  • Flask

  • GCP

      

      

        
Problem

        
At BirdieBox, sales built client orders by hand, and product and stock data was typed twice, once in Odoo and once in Shopify.

        
What I built

        
An internal portal where sales sets client-specific prices and creates draft orders in Shopify. A middleware on GCP that syncs products and inventory both ways between Odoo and Shopify. A script that creates 1,000+ discount codes per run.
